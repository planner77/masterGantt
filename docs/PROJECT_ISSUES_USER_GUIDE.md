# 프로젝트 Issue 사용 가이드 — #838–#840 / #846 / #849 (2026-10-29)

## 목적·조회 권한
프로젝트 상세 **일정 옆 Issue 탭**은 현장의 문제/조치 기록을 관리하는 별도 원장이다. GitHub 개발 이슈 및 WBS Task/Milestone과 독립이다. Issue 편집은 일정·진척률을 변경하지 않는다.

- **공개 프로젝트**: 로그인/편집 세션 없이 Issue 목록·상세를 읽을 수 있다.
- **비공개 프로젝트**: 기존 프로젝트 **편집 세션으로 읽기 권한을 먼저 확보**해야 한다. Issue 비밀번호만으로 프로젝트 조회가 열리지 않는다.
- **신규 Issue 등록**: 기존 프로젝트 편집 잠금 해제(편집 세션)가 필요하다. Issue 비밀번호만으로 신규 등록할 수 없다.
- **기존 Issue 수정·삭제**: 해당 Issue에 설정된 별도 **Issue 비밀번호**가 필요하다. 공개 프로젝트의 읽기 전용 사용자도 정확한 비밀번호를 알고 있으면 수정·삭제할 수 있다. 프로젝트 편집 세션만으로 보호된 Issue 수정·삭제가 허용되지는 않는다.

## Issue 등록
1. 프로젝트 → **Issue** 탭 → **Issue 등록** (프로젝트 편집 세션 필요).
2. **Issue 명**(필수 160자), 등록자/담당자(직접 입력 또는 프로젝트 리소스 검색), 발생일을 입력한다. 등록일은 서버가 기록하며 수정할 수 없다.
3. **관련 Task**는 **Issue 내용 위에** 있다. Task/Summary/Milestone을 검색 선택하면 정확한 Task ID·원본 이름 스냅샷이 등록된다. 직접 입력 시 연결 ID 없이 텍스트로만 보존된다. 타 프로젝트 Task/미참여 리소스는 연결할 수 없다.
4. **Issue 내용**에는 4,000자까지 줄바꿈/URL이 포함된 원문을 입력할 수 있다. 별도 '링크 미리보기' 영역은 제공하지 않는다.
5. **상태**는 등록(기본) / 진행 중 / 완료 중 하나를 고른다. 완료를 선택하면 Asia/Seoul 오늘 날짜가 완료일 기본값이 되며 수정할 수 있다. 등록·진행 중에는 완료일을 입력하지 않으며, 완료에서 변경 시 완료일을 지운다.
6. **Issue 비밀번호** 및 확인을 입력한다(8~128자, 제어문자 금지). 프로젝트 편집 비밀번호와 별도로 각 Issue마다 설정한다. **해당 비밀번호를 안전하게 보관**해야 한다. 서버는 복원 가능한 원문 대신 랜덤 salt와 scrypt 해시를 저장한다.
7. **등록**으로 저장한다. 같은 프로젝트에서 타 사용자가 먼저 변경했다면 412가 나오므로 최신 상태를 다시 조회한 후 재시도한다.

## 수정·논리 삭제
- 목록에서 Issue명을 선택하고 내용을 수정한다. 상태/완료일/담당자/Task/내용/제목 모두 동일하게 **Issue 비밀번호**를 요구한다. 저장 시 프로젝트 revision이 증가하며 다른 프로젝트 데이터 변경은 허용되지 않는다.
- 삭제는 상세 → **Issue 삭제…** → 경고 확인 → Issue 비밀번호 → **삭제 확인**으로 수행한다. 삭제된 Issue는 목록·검색·미완료/전체/등록/진행 중/완료 필터·페이지네이션·상태별 KPI에서 모두 제외된다.
- **논리 삭제**: DB에서는 `lifecycle_state=DELETED`와 `deleted_at`만 기록하며 제목·내용·완료 이력·작성시각·마지막 수정시각(`updated_at`)·관련 이름 스냅샷은 보존한다. 일반 API로는 숨겨지고 다시 수정할 수 없다. Issue 목록의 휴지통/복구 UI는 제공하지 않는다.
- 다른 사용자에 의해 변경되면 **412**가 표시된다. 잘못된 비밀번호는 **401**, 반복 인증은 **429**(Retry-After)로 제한될 수 있다. 삭제 요청을 반복해도 삭제된 레코드는 일반 접근에서 **404** 처리된다.

## 기존 Issue의 최초 비밀번호 설정·분실 복구
- Migration 0033 이전에 등록된 Issue는 **비밀번호 미설정**으로 표시된다. 기존 레코드에 임의/빈/공통 기본 비밀번호를 배정하지 않으며, 비밀번호 설정 전에는 누구도 수정·삭제할 수 없다.
- 프로젝트 **편집 세션 보유자**가 해당 Issue 상세에서 **Issue 비밀번호 최초 설정**을 열고 **현재 프로젝트 편집 비밀번호**를 다시 입력해 최초 설정한다. 프로젝트 편집 세션만 갖고서는 이 작업을 완료할 수 없다.
- 비밀번호 분실 시 같은 관리자가 **Issue 비밀번호 재설정**에서 프로젝트 편집 세션과 실제 프로젝트 편집 비밀번호를 모두 제시해야 한다. 이전 비밀번호는 읽을 수 없다. 최초 설정과 재설정은 `project_issue_credential_audit`에 동작·프로젝트/Issue·편집 세션 ID·request ID·시각만 감사 기록한다(비밀값 없음).
- 해당 경로는 명시적인 **credential 재설정**만 허용하며 Issue 본문/완료/삭제의 관리자 우회가 아니다. 비공개 프로젝트 read gate 및 Origin/If-Match를 그대로 따른다.

## 검색·KPI·동시성
- **전체 T건 / 완료 C건(P%) / 진행 중 P건(P%) / 등록 R건(P%)**: 검색/상태/페이지와 무관한 현재 프로젝트의 **삭제되지 않은** 모든 Issue가 분모다. T=C+P+R, 0건은 각 0.0%. 예: 전체 20/완료 5(25.0%)/진행 중 8(40.0%)/등록 7(35.0%).
- 검색: 제목·내용·등록자·담당자·관련 Task 텍스트. 상태 필터는 **미완료(등록+진행 중, 최초/초기화 기본) / 전체 / 등록 / 진행 중 / 완료**이며 '삭제'는 노출하지 않는다. 기본 필터라도 상단 통계는 전체 프로젝트 기준이다.
- 컬럼 **Issue명 / 상태 / 담당자 / 발생일 / 완료일**, 최신 등록순. 페이지당 10/20/50/100건, 검색/상태/limit 변경 시 첫 페이지. 기존 완료/미완료 행은 각각 완료/등록으로 이관되며 과거 진행 상태는 추정하지 않는다.
- 어떤 Issue 변경도 프로젝트 revision을 증가시킨다. 따라서 동시 WBS/Gantt 편집의 stale 412가 가능하지만 **Issue 비밀번호만으로 Task/WBS를 변경할 수 없다**.
- Task/리소스 원본 삭제 시 연결 FK는 NULL이 될 수 있지만 과거 Issue 이름/텍스트 스냅샷은 보존된다.

## 운영·보안
비밀번호는 URL, GET 결과, 로그, 로컬 스토리지에 남기지 않는다. Origin 검증/CSRF, JSON body 제한, 강한 If-Match, 인증 rate limit, 서버 KDF, 사후 transaction 재검증이 적용된다. 배포 환경이 여러 프로세스인 경우 현재 인메모리 rate limit은 각 프로세스 기준이므로 프록시 공통 인증 제한이 추가로 필요하다. 프로젝트 자체 삭제는 기존 FK CASCADE 및 백업 복구 계약을 따르며 Issue 논리 삭제와 다르다.
